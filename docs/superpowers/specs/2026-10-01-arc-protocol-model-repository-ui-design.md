# 《魔导协议》模型仓库与清晰化界面设计

- 日期：2026-10-01
- 页面：index.html
- 范围：单页原生 HTML/CSS/JavaScript 原型

## 目标

本次调整服务于两个目标：第一，让战斗、模型状态和后训练养成在视觉上分区清楚；第二，增加页面内的模型仓库，让 DeepSeek、Kimi、MiniMax 三具素体具有可读、可追踪的管理卡片。

不引入外部 CDN、远程图片、网络模型调用、存档或抽卡。模型仓库是游戏内的展示与管理界面，不是外部模型权重下载器。

## 已评估方案

### 方案 A：作战驾驶舱 + 常驻模型仓库（采用）

中部采用双栏结构：左侧为模型仓库，右侧为当前战斗；后训练驾驶舱保持在底部常驻。优点是模型状态、战斗结果和成长入口同时可见，最符合“后训练是主要养成系统”的目标。

### 方案 B：Tab 切换

把战斗、仓库、训练拆成 Tab。优点是单屏更简洁，缺点是训练预览与战斗反馈不能同时观察，隐藏了养成关联，因此不采用。

### 方案 C：所有信息横向卡片化

把战斗、仓库、训练都变成横向卡片。优点是信息密度高，缺点是桌面端拥挤、移动端容易产生横向溢出，因此不作为主布局。

## 信息架构

页面从上到下分为四层：

1. **协议状态总览**：当前深度、源质容量、已写入点、离线 LOG、训练指令和战斗状态。
2. **作战区**：模型仓库与当前战斗双栏展示。
3. **后训练驾驶舱**：配比滑杆、训练指令、实时预览、五维成长条和训练结算。
4. **诊断区**：tick 战报、卡关评估报告和导出蓝图操作。

移动端切换为单列顺序：总览 → 模型仓库 → 战斗 → 后训练 → 诊断。

## 模型仓库

模型仓库显示三张素体卡片：DeepSeek、Kimi、MiniMax。每张卡片包括：

- 模型名称、缩写和自包含的品牌几何标记；
- 素体编号和当前状态（战斗中 / 待命）；
- 主适性与角色标签；
- HP / 最大 HP；
- Bulwark、Vanguard、Marksman、Weaver、Conductor 五维微型成长条；
- 当前训练贡献或本次训练增量；
- 伤害、承伤、治疗贡献摘要；
- “聚焦”按钮与当前聚焦边框。

模型数据来自真实运行时 state 和当前 battle，不使用重复的静态数值。训练完成后，三张卡片随 state.vector 刷新。

“聚焦”只改变阅读焦点和卡片高亮，不改变战斗胜负、伤害、治疗、指令或训练数值，避免展示层行为污染核心逻辑。

## 清晰化视觉规则

- 每个主要区块使用明确的中文标题和一句用途说明；
- 关键数值采用更高对比度和统一等宽数字；
- 将英文模型代号作为辅助信息，不让其替代中文标签；
- 使用状态灯区分战斗中、待命、胜利和失败；
- 训练区域标出“配置 → 预览 → 执行”三个步骤；
- 保留现有攻击动画、伤害数字、治疗数字和 tick 战报；
- 卡片使用颜色、边框和几何标记区分模型，不依赖外部图标；
- 所有新增网格使用 minmax(0, 1fr) 或移动端单列，避免横向溢出。

## 数据流与边界

- 仓库卡片读取 `state.vector`、`state.battle.allies` 和当前战斗状态；
- 后训练成功后调用统一渲染入口，刷新仓库与战斗数据；
- 预览仍然只读，不消耗日志、不修改 `state.vector`；
- 训练失败时清除旧结算卡，不展示过期结果；
- `buildBattle()` 和 tick 计算继续使用真实 `state.vector`；
- 不修改 P(d)、C(d) 公式和 d1-d15 范围；
- 不加入 localStorage、sessionStorage、IndexedDB 或网络持久化。

## 验收标准

- 桌面端能同时看见模型仓库与当前战斗；
- 移动端不出现横向滚动；
- 三个模型卡片的名称、状态、HP、五维向量和贡献信息可辨识；
- 点击聚焦只影响高亮，不影响战斗数值；
- 训练执行后仓库数据更新；
- 既有训练、动画、卡关报告和导出蓝图测试继续通过；
- 无外部资源和持久化存储。
